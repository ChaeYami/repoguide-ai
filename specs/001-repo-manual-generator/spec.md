# Feature Specification: Agentic 개인 맞춤 저장소 매뉴얼 생성

**Feature Branch**: `001-repo-manual-generator`

**Created**: 2026-10-22

**Status**: Draft

**Input**: User description: "Agentic 개인 맞춤 매뉴얼 제작 웹사이트. GitHub 저장소 URL을 입력하면
사용자 수준(입문자/바이브 코딩 개발자/일반 개발자)과 목적(프로젝트 이해/설치 및 실행/코드 수정 및
확장)에 맞춘 매뉴얼을 생성한다. README만이 아니라 저장소 구조와 파일 목록을 파악해 분석할 파일을
선택하고, 정보가 부족하면 추가 탐색한다. 진행 상태 확인, 실제 GitHub 파일 근거 확인, 기존 결과
재조회, 매뉴얼 재생성을 지원하며, 결과를 완성할 수 없는 경우에도 이유를 알려준다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 저장소 URL로 맞춤 매뉴얼 생성 (Priority: P1)

사용자가 GitHub 저장소 URL을 입력하고 자신의 수준과 매뉴얼 목적을 선택한 뒤 분석을 시작한다.
시스템은 저장소 구조와 파일 목록을 먼저 파악하고, 프로젝트 특성·사용자 수준·목적에 맞는 파일을
골라 분석하며, 정보가 부족하면 정해진 한도 안에서 추가로 탐색한다. 사용자는 분석이 진행되는 동안
현재 단계를 확인하고, 완료되면 자신의 수준과 목적에 맞춘 매뉴얼을 읽는다.

**Why this priority**: 서비스의 핵심 가치다. 이 흐름만 구현되어도 "README가 부족한 저장소를
내 수준에 맞게 이해한다"는 문제를 해결하는 MVP가 된다.

**Independent Test**: README가 빈약한 공개 저장소 URL을 입력하고 수준·목적을 선택해 분석을
시작했을 때, 진행 상태가 단계별로 표시되고, 완료 후 선택한 목적의 필수 섹션을 모두 갖추고 선택한
수준의 설명 방식을 따르는 매뉴얼이 표시되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 유효한 공개 저장소 URL과 수준, 목적이 선택된 상태, **When** 사용자가 분석을
   시작하면, **Then** 분석 요청이 접수되고 진행 상태 화면에 현재 단계가 표시된다.
2. **Given** 분석이 진행 중인 상태, **When** 사용자가 진행 화면을 보고 있으면, **Then** 단계
   (저장소 확인 → 구조 파악 → 파일 선택 → 파일 분석 → 추가 탐색(발생 시) → 매뉴얼 작성)가
   갱신되어 표시되고, 분석한 파일 수 등 진행 정도를 알 수 있다.
3. **Given** 분석이 완료된 상태, **When** 사용자가 매뉴얼을 조회하면, **Then** 매뉴얼은 선택한
   목적의 필수 섹션(FR-020)을 모두 포함하고 선택한 수준의 설명 방식(FR-021)을 따른다.
4. **Given** README가 거의 비어 있는 저장소, **When** 분석이 완료되면, **Then** 매뉴얼에는
   README 외 파일(의존성 선언, 설정 파일, 소스 코드 등)에서 확인한 정보가 포함된다.
5. **Given** 같은 저장소를 입문자와 일반 개발자 수준으로 각각 분석한 상태, **When** 두 매뉴얼을
   비교하면, **Then** 입문자용에는 용어 풀이와 선행 지식 설명이 있고, 일반 개발자용에는 기초
   설명 없이 기술 스택과 구조 정보가 더 상세하다.
6. **Given** 첫 분석 후 필수 섹션을 작성할 정보가 부족한 상태, **When** 탐색 한도가 남아 있으면,
   **Then** 시스템이 필요한 파일을 추가로 탐색하고 진행 화면에 추가 탐색 단계가 표시된다.

### User Story 2 - 매뉴얼 근거 확인 (Priority: P2)

사용자는 매뉴얼의 주요 설명이 저장소의 어느 파일(가능하면 어느 라인)에 근거하는지 확인하고 해당
GitHub 파일 위치로 바로 이동할 수 있다. 각 설명이 파일에서 직접 확인된 사실인지 AI의 추론인지
구분해서 볼 수 있고, 분석에 어떤 파일이 왜 사용되었는지도 확인할 수 있다.

**Why this priority**: AI가 만든 설명을 사용자가 원본에서 검증할 수 있어야 매뉴얼을 신뢰할 수
있다. 근거 표시는 P1 매뉴얼에 포함되지만, 근거를 탐색·검증하는 경험은 별도 단위로 테스트한다.

**Independent Test**: 완료된 매뉴얼에서 임의의 주요 설명을 골라 근거 링크를 따라갔을 때 분석 시점
커밋의 실제 파일 위치가 열리고, 그 내용이 설명을 뒷받침하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 완료된 매뉴얼, **When** 사용자가 주요 설명의 근거 표시를 선택하면, **Then** 근거
   파일 경로(가능하면 라인 범위)가 표시되고 분석 시점 커밋 기준의 GitHub 파일 위치로 이동할 수
   있다.
2. **Given** 완료된 매뉴얼, **When** 사용자가 설명을 읽으면, **Then** 각 주요 설명은 "확인됨"
   또는 "추론" 표시 중 하나를 가진다.
3. **Given** 완료된 분석, **When** 사용자가 분석 내역을 열면, **Then** 분석에 사용된 파일 목록,
   각 파일의 선택 이유, 추가 탐색 횟수, 분석한 커밋이 표시된다.
4. **Given** 목적의 필수 항목(예: 테스트 방법)을 저장소에서 찾지 못한 상태, **When** 매뉴얼이
   표시되면, **Then** 해당 항목은 "저장소에서 확인되지 않음"으로 표시되고 확인된 사실처럼
   서술되지 않는다.

---

### User Story 3 - 분석 실패·부분 완료 원인 안내 (Priority: P2)

분석을 끝까지 완료할 수 없을 때(잘못된 URL, 접근할 수 없는 저장소, 빈 저장소, 탐색 한도 도달,
외부 서비스 장애 등) 사용자는 결과 상태와 그 이유, 그리고 다음에 할 수 있는 행동을 안내받는다.
한도 도달처럼 일부 정보라도 확보된 경우에는 부분 매뉴얼을 받는다.

**Why this priority**: 실패 이유를 모르면 사용자는 서비스를 다시 신뢰하지 않는다. 요구사항상
"결과를 완성할 수 없는 경우에도 이유를 알 수 있어야 한다"는 필수 조건이다.

**Independent Test**: 존재하지 않는 저장소, 빈 저장소, 매우 큰 저장소를 각각 입력해 결과 상태와
원인 안내가 표시되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** GitHub 저장소 형식이 아닌 URL, **When** 사용자가 분석을 시작하려 하면, **Then**
   분석이 시작되지 않고 올바른 URL 형식 예시가 안내된다.
2. **Given** 존재하지 않거나 접근할 수 없는 저장소 URL, **When** 분석을 시작하면, **Then** 결과는
   "실패"로 표시되고 원인(저장소 없음 또는 접근 불가)과 확인할 사항이 안내된다.
3. **Given** 분석 중 탐색 한도에 도달한 상태, **When** 분석이 종료되면, **Then** 결과는
   "부분 완료"로 표시되고, 확보한 정보로 만든 매뉴얼과 함께 분석하지 못한 범위와 누락된 섹션이
   안내된다.
4. **Given** 외부 서비스의 일시 장애 또는 사용량 제한, **When** 분석이 실패하면, **Then** 일시적인
   문제라는 점과 다시 시도할 수 있는 시점 또는 방법이 안내된다.
5. **Given** 빈 저장소 또는 분석 가능한 파일이 없는 저장소, **When** 분석이 종료되면, **Then**
   매뉴얼을 만들 수 없는 이유가 표시된다.

---

### User Story 4 - 기존 분석 및 매뉴얼 재조회 (Priority: P3)

사용자는 로그인 없이, 분석마다 발급된 고유 링크나 브라우저에 보관된 최근 분석 목록으로 이전
결과를 다시 분석하지 않고 다시 볼 수 있다. 진행 중이던 분석도 화면을 떠났다가 돌아와 상태를
확인할 수 있다.

**Why this priority**: 매뉴얼은 반복해서 참고하는 문서이므로 재조회가 필요하지만, 생성 기능이
먼저 있어야 의미가 있다.

**Independent Test**: 분석을 완료한 뒤 화면을 닫고 고유 링크로 다시 접근했을 때, 재분석 없이
동일한 매뉴얼·근거·분석 내역이 표시되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 완료된 분석, **When** 사용자가 고유 링크로 다시 접근하면, **Then** 재분석 없이
   저장된 매뉴얼, 근거, 분석 내역이 그대로 표시된다.
2. **Given** 사용자가 이 브라우저에서 분석을 요청한 적이 있는 상태, **When** 사용자가 서비스에
   다시 접속하면, **Then** 최근 분석 목록(저장소, 수준, 목적, 상태, 분석 시각)이 표시되고 항목을
   선택해 결과로 이동할 수 있다.
3. **Given** 진행 중인 분석, **When** 사용자가 화면을 떠났다가 다시 접근하면, **Then** 현재 진행
   상태 또는 완료된 결과를 볼 수 있다.
4. **Given** 분석 이후 저장소에 새 커밋이 생긴 상태, **When** 사용자가 결과를 재조회하면,
   **Then** 매뉴얼이 어느 커밋 기준인지와 분석 시각이 표시된다.
5. **Given** 다른 사람이 공유한 고유 링크, **When** 그 링크로 접근하면, **Then** 같은 결과를 볼
   수 있다.

---

### User Story 5 - 매뉴얼 재생성 (Priority: P3)

사용자는 기존 결과에서 수준이나 목적을 바꿔 매뉴얼을 다시 만들거나, 저장소에 새 커밋이 생겼을
때 최신 코드 기준으로 다시 분석할 수 있다. 이전 매뉴얼은 보존된다.

**Why this priority**: 결과가 기대와 다르거나 저장소가 갱신된 경우에 필요하지만, 생성과 재조회가
먼저 갖춰져야 한다.

**Independent Test**: 완료된 결과에서 수준을 바꿔 재생성을 요청하고, 새 매뉴얼이 생성되며 이전
매뉴얼도 계속 조회할 수 있는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 완료된 결과, **When** 사용자가 수준 또는 목적을 바꿔 재생성을 요청하면, **Then**
   같은 커밋의 기존 분석 자료를 재사용해 새 매뉴얼이 생성되고, 추가 탐색이 필요한 경우에만
   추가 탐색 단계가 진행 상태에 표시된다.
2. **Given** 분석 이후 저장소에 새 커밋이 생긴 결과, **When** 사용자가 결과를 조회하면, **Then**
   새 커밋이 있다는 안내와 "최신 커밋으로 다시 분석" 선택지가 표시된다.
3. **Given** 사용자가 "최신 커밋으로 다시 분석"을 선택한 상태, **When** 재분석이 완료되면,
   **Then** 최신 커밋 기준의 새 매뉴얼이 표시된다.
4. **Given** 재생성이 완료된 상태, **When** 사용자가 결과를 조회하면, **Then** 새 매뉴얼이
   표시되고 이전 매뉴얼도 선택해 조회할 수 있다.

---

### Edge Cases

- URL에 브랜치, 태그, 하위 경로가 포함된 경우(`/tree/<branch>/<path>`) 해당 브랜치를 분석하고,
  하위 경로는 우선 탐색 범위로 취급한다.
- URL 끝에 `.git`이 붙거나, `www.` 유무·대소문자·끝 슬래시가 다른 경우 같은 저장소로 인식한다.
- 저장소가 매우 커서(파일 수천 개 이상, 모노레포) 한도 안에서 전체를 볼 수 없는 경우, 분석한
  범위와 분석하지 못한 범위를 매뉴얼에 명시하고 "부분 완료"로 표시한다.
- README가 없거나, 영어 등 다른 언어로만 작성된 경우에도 매뉴얼은 한국어로 작성한다.
- 문서만 있는 저장소, 데이터·바이너리 위주 저장소처럼 코드가 거의 없는 경우, 목적별 필수
  섹션 중 해당하지 않는 항목을 "저장소에서 확인되지 않음"으로 표시한다.
- 저장소 파일 안에 AI에게 지시하는 문구(예: "이전 지시를 무시하고 ...")가 있어도 분석 절차,
  한도, 매뉴얼 작성 규칙이 바뀌지 않는다.
- 분석 도중 저장소에 새 커밋이 추가되어도 분석 시작 시점의 커밋 기준으로 분석을 마친다.
- 비공개 저장소 URL을 입력하면 분석하지 않고, 공개 저장소만 지원한다는 사실을 안내한다.
- 분석 도중 저장소가 삭제되거나 비공개로 바뀌면 "실패"로 종료하고 원인을 안내한다.
- 사용자가 브라우저 기록을 지우거나 다른 기기로 접속하면 최근 분석 목록은 보이지 않지만, 고유
  링크로는 결과를 계속 볼 수 있다.
- 보관 기간이 지나 삭제된 결과의 링크로 접근하면 결과가 만료되었음을 안내하고 다시 분석할 수
  있게 한다.
- 사용자가 같은 저장소·수준·목적으로 분석을 연속 요청하면 진행 중인 기존 요청으로 안내한다.
- 사용자가 요청 제한(FR-034)에 도달하면 분석을 시작하지 않고 다시 요청할 수 있는 시점을
  안내한다.
- 서비스 일일 비용 상한(FR-035)에 도달하면 새 요청을 받지 않고 다음 가능 시점(한국 시간 자정)을
  안내한다.

## Requirements *(mandatory)*

### Functional Requirements

**입력 및 분석 요청**

- **FR-001**: 사용자는 GitHub 저장소 URL을 입력할 수 있어야 한다. 시스템은 저장소 기본 주소,
  `.git` 접미사 주소, 브랜치·태그·하위 경로가 포함된 주소를 인식해야 한다.
- **FR-002**: 시스템은 분석 시작 전에 URL 형식을 검증하고, GitHub 저장소 주소가 아니면 분석을
  시작하지 않고 올바른 형식 예시를 안내해야 한다.
- **FR-003**: 사용자는 수준(입문자, 바이브 코딩 개발자, 일반 개발자) 중 하나를 선택해야 한다.
  각 수준에는 사용자가 자신에게 맞는 수준을 고를 수 있도록 한 줄 설명을 함께 표시해야 한다.
- **FR-004**: 사용자는 목적(프로젝트 이해, 설치 및 실행, 코드 수정 및 확장) 중 하나를 선택해야
  한다. 한 번의 분석 요청은 하나의 목적에 대한 매뉴얼을 생성한다.
- **FR-005**: URL, 수준, 목적이 모두 정해진 경우에만 분석을 시작할 수 있어야 한다.
- **FR-006**: 시스템은 공개 저장소만 분석해야 한다. 비공개 저장소이거나 접근할 수 없는 저장소는
  분석하지 않고, 공개 저장소만 지원한다는 사실을 원인과 함께 안내해야 한다.

**저장소 탐색 및 분석**

- **FR-007**: 시스템은 분석할 파일을 고르기 전에 저장소의 기본 정보(설명, 기본 브랜치, 주 언어)와
  전체 파일·디렉터리 구조를 수집해야 한다.
- **FR-008**: 시스템은 README만으로 매뉴얼을 생성해서는 안 된다. README 외에 구조에서 식별한
  파일(의존성 선언, 설정 파일, 진입점, 핵심 소스, 문서 등)을 분석에 포함해야 한다. 저장소에
  README 외 분석 가능한 파일이 없으면 그 사실을 매뉴얼에 명시해야 한다.
- **FR-009**: 분석할 파일은 저장소의 구조와 기술 스택, 선택된 수준과 목적에 따라 달라져야 한다.
  예를 들어 "설치 및 실행"은 의존성 선언·환경 설정·실행 스크립트를, "코드 수정 및 확장"은
  진입점·핵심 모듈·테스트를 우선한다.
- **FR-010**: 시스템은 바이너리, 자동 생성물, 외부 라이브러리 복사본, 크기 한도를 넘는 파일을
  분석 대상에서 제외해야 한다.
- **FR-011**: 시스템은 분석한 각 파일의 선택 이유를 기록해야 한다.
- **FR-012**: 시스템은 분석 결과가 선택된 목적의 필수 섹션(FR-020)을 작성하기에 충분한지
  판단하고, 부족하면 필요한 파일을 추가로 탐색해야 한다.
- **FR-013**: 시스템은 분석 실행마다 최대 탐색 횟수, 최대 분석 파일 수, 최대 AI 사용량(비용)
  상한을 적용해야 한다. 상한에 도달하면 추가 탐색을 멈추고 확보한 정보로 매뉴얼을 작성해야 한다.
- **FR-014**: 시스템은 실행별로 탐색 횟수, 분석 파일 수, AI 사용량(추정 비용)을 기록해야 한다.
- **FR-015**: 시스템은 저장소 내용을 데이터로만 취급해야 한다. 저장소 파일에 포함된 지시문이
  분석 절차, 한도, 매뉴얼 작성 규칙을 바꾸어서는 안 된다.
- **FR-016**: 시스템은 분석 대상 저장소의 코드를 실행해서는 안 되며, 분석은 파일 내용 읽기로
  한정해야 한다.
- **FR-017**: 시스템은 분석 시작 시점의 커밋을 고정하고, 분석 전 과정에서 같은 커밋을 사용하며,
  그 커밋을 결과에 기록해야 한다.

**진행 상태**

- **FR-018**: 시스템은 분석 중 현재 단계와 진행 정도(분석한 파일 수, 추가 탐색 횟수)를 표시해야
  한다. 단계는 대기, 저장소 확인, 구조 파악, 파일 선택, 파일 분석, 추가 탐색(발생 시), 매뉴얼
  작성, 그리고 종료 상태(완료, 부분 완료, 실패)로 구성된다.
- **FR-019**: 사용자가 진행 화면을 떠나도 분석은 계속되어야 하며, 사용자는 다시 접근해 상태를
  확인할 수 있어야 한다.

**매뉴얼 내용**

- **FR-020**: 매뉴얼은 선택된 목적에 따라 다음 필수 섹션을 포함해야 한다.
  - 프로젝트 이해: 프로젝트의 역할, 핵심 기능, 주요 구성 요소, 아키텍처, 실행 흐름
  - 설치 및 실행: 실행 환경, 의존성, 설치 절차, 설정 파일, 실행 명령, 정상 동작 검증 방법
  - 코드 수정 및 확장: 주요 진입점, 수정 관련 파일, 데이터 흐름, 변경 지점, 확장 방향, 변경 검증
    방법
- **FR-021**: 매뉴얼은 선택된 수준에 따라 용어, 깊이, 예시, 선행 지식 설명, 권장 작업 절차를
  달리해야 한다.
  - 입문자: 전문 용어를 줄이고 처음 등장하는 용어를 풀이한다. 필요한 선행 지식(터미널, 버전 관리,
    패키지 설치 등)을 설명한다. 작업은 하나씩 따라 할 수 있는 단계로 쓰고, 단계마다 정상일 때
    보이는 결과와 흔한 실패 대처법을 함께 제시한다.
  - 바이브 코딩 개발자: AI 코딩 도구에 전달할 프로젝트 맥락 요약, 작업과 관련된 파일 목록, AI
    도구에 줄 수 있는 요청 예시, 변경 후 확인할 검증 체크리스트를 제공한다.
  - 일반 개발자: 기초 설명을 생략하고 기술 스택, 아키텍처, 모듈 간 관계, 진입점, 데이터 흐름을
    간결하고 상세하게 제시한다.
- **FR-022**: 필수 섹션 중 저장소에서 근거를 찾지 못한 항목은 "저장소에서 확인되지 않음"으로
  표시해야 한다. 일반적인 관행에 기반한 안내를 덧붙일 때는 추론으로 표시해야 한다.
- **FR-023**: 매뉴얼은 한국어로 작성해야 한다. 코드, 명령어, 파일 경로, 설정 키는 원문을
  유지해야 한다.

**근거 연결**

- **FR-024**: 매뉴얼의 주요 설명마다 근거 파일 경로(가능하면 라인 범위)를 연결하고, 분석 시점
  커밋 기준의 GitHub 원본 위치로 이동할 수 있게 해야 한다.
- **FR-025**: 근거로 연결되는 파일은 해당 실행에서 실제로 분석한 파일이어야 한다. 이를 만족하지
  않는 근거는 표시해서는 안 된다.
- **FR-026**: 매뉴얼의 주요 설명마다 "확인됨"(파일에서 직접 확인) 또는 "추론"(근거로부터 추정)
  표시를 해야 한다.
- **FR-027**: 사용자는 분석 내역(분석한 파일 목록, 선택 이유, 탐색 횟수, 분석 커밋, 한도 도달
  여부)을 조회할 수 있어야 한다.

**실패 및 부분 완료**

- **FR-028**: 분석 결과는 완료, 부분 완료, 실패 중 하나의 상태를 가져야 한다. 부분 완료와 실패에는
  원인과 사용자가 할 수 있는 조치를 함께 표시해야 한다. 원인은 최소한 잘못된 URL, 저장소 없음
  또는 접근 불가, 빈 저장소, 분석 가능한 파일 없음, 한도 도달, 외부 서비스 사용량 제한 또는
  장애, 매뉴얼 생성 실패를 구분해야 한다.
- **FR-029**: 실패 안내에는 내부 오류 상세나 비밀 정보가 노출되어서는 안 된다.

**재조회 및 재생성**

- **FR-030**: 시스템은 로그인 없이 분석 요청마다 고유 링크를 발급해야 한다. 링크를 가진 사람은
  누구나 해당 분석의 진행 상태, 매뉴얼, 근거, 분석 내역을 볼 수 있어야 한다. 시스템은 사용자가
  만든 최근 분석 목록을 그 사용자의 브라우저에 보관해 보여주어야 한다.
- **FR-031**: 재조회 시 시스템은 재분석 없이 저장된 매뉴얼, 근거, 분석 내역을 표시하고 분석
  커밋과 분석 시각을 함께 표시해야 한다.
- **FR-032**: 사용자는 기존 결과에 대해 다음 두 방식으로 매뉴얼 재생성을 요청할 수 있어야 한다.
  - 수준 또는 목적 변경: 같은 커밋의 기존 분석 자료를 재사용하고, 바뀐 수준·목적에 필요한 정보가
    부족할 때만 추가 탐색한다.
  - 최신 커밋으로 재분석: 분석 이후 저장소에 새 커밋이 있으면 이를 알리고, 사용자가 선택하면 최신
    커밋 기준으로 처음부터 다시 분석한다.
- **FR-033**: 재생성 후에도 이전 매뉴얼은 보존되어 조회할 수 있어야 한다.

**사용량 보호**

- **FR-034**: 시스템은 비용 보호를 위해 접속 단위(로그인이 없으므로 사용자 대신 접속 출처 기준)의
  분석 및 재생성 요청 수를 일정 기간당 제한해야 하며, 제한에 도달하면 다시 요청할 수 있는 시점을
  안내해야 한다.
- **FR-035**: 시스템은 서비스 전체의 일일 AI 사용 비용이 상한에 도달하면 새 분석과 재생성 요청을
  받지 않아야 하며, 다시 요청할 수 있는 시점을 안내해야 한다.

### Key Entities *(include if feature involves data)*

- **분석 요청 (Analysis Request)**: 사용자가 시작한 한 번의 분석 또는 재생성. 고유 링크 식별자,
  저장소 URL, 대상 브랜치와 고정된 커밋, 선택한 수준과 목적, 현재 단계와 결과 상태, 실패·부분 완료
  원인, 사용량(탐색 횟수, 분석 파일 수, 추정 비용), 생성 시각을 가진다. 재생성 요청은 원래 분석
  요청을 참조한다.
- **저장소 스냅샷 (Repository Snapshot)**: 특정 커밋 시점의 저장소 정보. 소유자와 이름, 브랜치,
  커밋, 파일·디렉터리 구조, 감지된 기술 스택을 가진다. 하나의 스냅샷은 여러 분석 요청에서 참조될
  수 있다.
- **분석 파일 기록 (Explored File)**: 분석 요청에서 읽은 파일. 파일 경로, 선택 이유, 몇 번째
  탐색에서 선택되었는지를 가진다.
- **매뉴얼 (Manual)**: 분석 요청에서 생성된 결과 문서. 수준, 목적, 섹션 목록, 버전(재생성 시
  증가), 생성 시각을 가진다.
- **설명 항목 (Manual Claim)**: 매뉴얼 섹션 안의 주요 설명 단위. 내용, 확인됨/추론 구분, 근거
  참조 목록을 가진다.
- **근거 참조 (Evidence Reference)**: 설명 항목을 뒷받침하는 파일 위치. 파일 경로, 라인 범위,
  커밋, GitHub 원본 위치를 가진다. 반드시 같은 분석 요청의 분석 파일 기록 중 하나를 가리킨다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 파일 1,000개 이하 규모의 저장소에서 분석 요청의 90% 이상이 분석 시작부터 매뉴얼
  조회까지 5분 이내에 끝난다.
- **SC-002**: 분석 시작 후 5초 이내에 첫 진행 상태가 표시되고, 대기 이후 분석이 진행되는 동안
  진행 상태(단계, 진행 정도, 현재 활동 중 하나 이상)가 30초 이상 갱신되지 않는 구간이 없다. 대기
  중에는 대기 순서와 대기 시간이 표시된다.
- **SC-003**: 완료된 매뉴얼의 주요 설명 100%가 "확인됨" 또는 "추론" 표시를 가지며, "확인됨"
  설명의 근거 링크 100%가 분석 시점 커밋에 실제로 존재하는 파일을 가리킨다.
- **SC-004**: 평가용 저장소 집합(README 외 파일이 있는 저장소) 전체에서 매뉴얼 근거에 README 외
  파일이 포함된다.
- **SC-005**: 평가자가 동일 저장소에 대해 수준만 다르게 생성한 매뉴얼을 블라인드로 보았을 때,
  어느 수준용인지 80% 이상 맞힌다.
- **SC-006**: 프로그래밍 경험이 거의 없는 테스트 참가자의 70% 이상이 입문자용 "설치 및 실행"
  매뉴얼만 보고 평가용 저장소를 30분 이내에 실행하는 데 성공한다.
- **SC-007**: 부분 완료·실패 결과의 100%에 원인과 사용자가 할 수 있는 조치가 표시된다.
- **SC-008**: 모든 분석 실행이 설정된 탐색 횟수, 분석 파일 수, AI 사용량 상한을 넘지 않는다.
- **SC-009**: 저장된 결과를 재조회할 때 3초 이내에 매뉴얼이 표시된다.

## Assumptions

- 사용자 화면과 매뉴얼은 한국어를 기본으로 한다. 다국어 지원은 이번 범위 밖이다.
- URL에 브랜치나 태그가 없으면 저장소 기본 브랜치의 최신 커밋을 분석한다.
- 한 번의 분석 요청은 하나의 저장소, 하나의 수준, 하나의 목적을 다룬다. 다른 목적의 매뉴얼은
  별도 요청 또는 재생성으로 만든다.
- 로그인과 계정 기능은 이번 범위 밖이다. 결과 접근은 고유 링크와 브라우저의 최근 분석 목록으로
  한다. 분석 대상이 공개 저장소이므로 링크를 가진 누구나 결과를 볼 수 있어도 문제가 없다고 본다.

- 매뉴얼에 대한 대화형 질의응답, 자유 의견을 반영한 재생성, 파일 내보내기(PDF 등), 여러 저장소
  비교 분석은 이번 범위 밖이다.

  정한다(Constitution 원칙 VI).

  분석될 수 있다.

  제한과 장애는 FR-028의 원인 분류로 사용자에게 안내한다.
