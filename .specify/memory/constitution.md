

# RepoGuide AI Constitution

RepoGuide AI는 GitHub 저장소 URL을 입력받아, AI가 저장소의 실제 코드와 문서를 분석하고
사용자의 수준과 목적에 맞춘 매뉴얼을 생성하는 웹사이트다. 이 문서는 모든 명세(spec),
계획(plan), 작업(tasks), 구현이 따라야 하는 상위 원칙을 정의한다.

## Core Principles

### I. 동적 파일 선택 (Dynamic File Selection)

- 분석 대상 파일은 고정 목록이 아니라 저장소의 구조(디렉터리 트리), 기술 스택(매니페스트·설정
  파일 등), 사용자의 목적과 수준에 따라 실행마다 동적으로 선택되어야 한다(MUST).
- 바이너리, 생성물, 벤더 디렉터리, 크기 초과 파일 등 명백히 분석 가치가 없는 파일의 제외는
  규칙 기반 코드로 처리해야 한다(MUST). 남은 후보 중 무엇을 읽을지의 우선순위 판단은 LLM이
  담당할 수 있다(MAY).
- 각 실행은 어떤 파일을 왜 선택했는지(선택 근거)를 기록해야 한다(MUST).

근거: 저장소마다 핵심 정보의 위치가 다르므로 고정 규칙만으로는 품질이 보장되지 않고,
전체 파일을 읽는 방식은 비용 한도(원칙 VI)를 위반한다.

### II. 정보 충분성 판단과 추가 탐색 (Sufficiency-Driven Exploration)

- AI는 각 탐색 결과를 바탕으로 사용자 목적에 맞는 매뉴얼을 작성하기에 정보가 충분한지
  판단하고, 부족하면 필요한 추가 파일이나 정보를 구체적으로 요청할 수 있다(MAY).
- 추가 자료 요청은 구조화된 형식(요청 대상과 요청 이유)으로 표현되어야 하며, 실제 조회는
  원칙 III에 따라 일반 코드가 수행해야 한다(MUST).
- 추가 탐색은 원칙 VI의 한도 안에서만 허용된다. 한도에 도달하면 탐색을 종료하고 확보된
  정보로 매뉴얼을 작성하되, 부족한 부분을 사용자에게 명시해야 한다(MUST).

근거: 한 번의 고정 수집으로는 저장소 이해가 불완전할 수 있으나, 무제한 탐색은 비용과
지연을 통제할 수 없게 만든다.

### III. 결정적 처리는 일반 코드로 (Deterministic Work in Code)

- GitHub API 호출, 파일 목록·내용 조회, 파일 존재·크기·형식 검증, 데이터 저장, 한도 계산,
  인용 경로 검증 등 결정적으로 처리 가능한 작업은 일반 코드로 구현해야 한다(MUST).
- 이러한 작업을 LLM 프롬프트나 LLM 판단에 위임해서는 안 된다(MUST NOT).
- 결정적 처리 코드는 LLM 없이 독립적으로 테스트 가능해야 한다(MUST).

근거: 결정적 작업을 코드로 두면 재현 가능하고, 테스트 가능하며, 비용이 들지 않고,
LLM의 오류(환각)가 시스템 동작에 섞이지 않는다.

### IV. LLM은 판단이 필요한 곳에만 (LLM for Judgment Only)

- LLM은 코드·문서의 의미 분석, 추가 탐색 필요 여부 판단, 사용자 수준별 설명 생성처럼
  AI의 판단이 필요한 영역에만 사용한다(MUST).
- LLM 출력 중 시스템이 후속 처리하는 값(예: 파일 요청, 충분성 판단 결과)은 정의된 구조로
  받고, 코드가 형식과 유효성을 검증한 후에만 사용해야 한다(MUST).
- 새로운 LLM 호출 지점을 추가할 때는 Plan 문서에 해당 작업이 왜 결정적 코드로 대체될 수
  없는지 기록해야 한다(MUST).

근거: LLM을 필요한 곳에만 쓰면 비용과 오류 표면이 줄고, 각 LLM 호출의 책임이 명확해진다.

### V. 근거 연결과 사실·추론 구분 (Grounded Claims)

- 매뉴얼의 주요 설명은 이를 뒷받침하는 실제 저장소 파일(경로, 가능하면 라인 범위)과
  연결되어야 한다(MUST).
- 인용된 파일 경로는 해당 실행에서 실제로 조회된 파일인지 코드로 검증해야 하며, 검증에
  실패한 인용은 제거하거나 수정해야 한다(MUST).
- 매뉴얼은 파일에서 직접 확인된 사실과 AI의 추론을 사용자가 구분할 수 있도록 표시해야
  한다(MUST). 근거가 없는 설명을 확인된 사실로 제시해서는 안 된다(MUST NOT).
- 분석 결과는 분석 시점의 저장소 버전(브랜치 또는 커밋)을 함께 기록해야 한다(MUST).

근거: 사용자가 매뉴얼을 신뢰하고 원본에서 직접 검증할 수 있어야 하며, 저장소가 바뀌어도
어떤 시점의 코드를 설명한 것인지 알 수 있어야 한다.

### VI. 탐색·비용 한도 (Bounded Exploration & Cost)

- 모든 매뉴얼 생성 실행은 최대 탐색 횟수, 최대 조회 파일 수(및 파일 크기), 최대 토큰
  사용량, 최대 API 호출 비용에 대한 상한을 가져야 한다(MUST).
- 한도는 설정값으로 관리하고, LLM이 아닌 일반 코드가 강제해야 한다(MUST).
- 한도 도달 시 실행은 오류로 중단되지 않고 정상적으로 종료하며, 확보된 정보 범위와 한도
  도달 사실을 결과에 표시해야 한다(MUST).
- 각 실행의 탐색 횟수, 조회 파일 수, 토큰 사용량, 추정 비용을 기록해야 한다(MUST).
- 구체적인 기본 한도 수치는 Plan 단계에서 결정한다.

근거: Agentic 탐색은 반복 구조상 비용과 지연이 쉽게 폭증하므로, 상한이 없으면 서비스
운영과 사용자 경험을 보장할 수 없다.

### VII. 최소 Agentic 워크플로 우선 (Minimal Agentic Workflow First)

- 초기 구현은 원칙 I·II를 충족하는 데 필요한 최소한의 에이전트와 단계로 구성해야
  한다(MUST).
- 에이전트, 단계, 도구를 추가하려면 현재 구조로 해결되지 않는 구체적 문제(실패 사례 또는
  품질·비용 측정 결과)를 근거로 제시하고, Plan 문서의 Complexity Tracking에 기록해야
  한다(MUST).
- 추측에 기반한 확장(“나중에 필요할 수도 있음”)은 허용하지 않는다(MUST NOT).

근거: 에이전트와 단계가 늘어날수록 비용, 지연, 디버깅 난이도가 커지므로, 필요성이 검증된
경우에만 복잡도를 늘린다.

## 보안 및 데이터 취급 제약 (Security & Data Handling Constraints)

- 분석 대상 저장소의 파일 내용은 신뢰할 수 없는 입력 데이터로 취급해야 한다(MUST). 파일
  안에 포함된 지시문이 시스템이나 LLM의 동작 지시로 처리되어서는 안 된다(MUST NOT).
- 분석 대상 저장소의 코드를 실행해서는 안 된다(MUST NOT). 분석은 파일 내용 읽기로 한정한다.
- GitHub 토큰, LLM API 키 등 비밀값은 서버 측에서만 보관·사용하고, 클라이언트 응답,
  로그, 생성된 매뉴얼에 노출되어서는 안 된다(MUST NOT).
- GitHub API 사용량 제한(rate limit)과 오류 응답은 코드에서 감지하고 사용자에게 이해 가능한
  메시지로 전달해야 한다(MUST).

## 개발 워크플로 및 품질 게이트 (Development Workflow & Quality Gates)

- 기능 개발은 Spec-Kit 흐름(specify → clarify(필요 시) → plan → tasks → implement)을
  따른다.
- 구체적인 Agentic 실행 구조(루프 형태, 에이전트 구성, 단계 정의)와 기술 스택 선택은 Plan
  단계에서 대안을 비교·검토한 뒤 결정하고, 선택 근거를 Plan 문서에 기록해야 한다(MUST).
- 모든 Plan은 "Constitution Check"에서 최소한 다음 게이트를 확인해야 한다(MUST).
  - 결정적 처리와 LLM 판단 영역이 분리되어 있는가 (원칙 III, IV)
  - 파일 선택과 추가 탐색이 근거와 함께 기록되는가 (원칙 I, II)
  - 매뉴얼 설명의 파일 연결, 인용 검증, 사실·추론 구분 방식이 정의되어 있는가 (원칙 V)
  - 탐색·파일·토큰·비용 한도와 그 강제 지점이 정의되어 있는가 (원칙 VI)
  - 에이전트·단계 추가가 있다면 검증된 근거가 Complexity Tracking에 있는가 (원칙 VII)
- 결정적 처리 코드(GitHub 연동, 파일 검증, 한도 계산, 인용 검증)는 자동화된 테스트를
  갖춰야 한다(MUST).

## Governance

- 이 Constitution은 RepoGuide AI의 다른 모든 개발 관행과 문서보다 우선한다. 충돌 시 이
  문서를 따르거나, 먼저 이 문서를 개정한다.
- 개정 절차: 변경 내용과 사유를 작성하고, 영향을 받는 spec·plan·tasks를 식별한 뒤,
  `/speckit-constitution`으로 이 문서를 갱신한다. 개정 시 Sync Impact Report를 함께
  작성한다.
- 버전 정책(Semantic Versioning):
  - MAJOR: 원칙의 삭제 또는 하위 호환되지 않는 재정의
  - MINOR: 새 원칙·섹션 추가 또는 지침의 실질적 확장
  - PATCH: 의미 변화 없는 문구 수정, 명확화, 오타 수정
- 준수 검토: 모든 Plan은 Constitution Check 게이트를 통과해야 하며(Phase 0 이전, Phase 1
  설계 이후 재확인), 원칙 위반이 불가피한 경우 Complexity Tracking에 사유와 기각된 단순
  대안을 기록해야 한다. 코드 리뷰는 변경 사항이 원칙 III–VI를 위반하지 않는지 확인한다.
